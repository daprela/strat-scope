# Backtest Viewer Run Bundle Contract v1.0.0

**Contract status:** AUTHORED NORMATIVE CONTRACT. **Format identifier:** `1.0.0`. **Date:** 2026-10-10.

This is the first complete specification. It replaces the preceding draft bearing the same version label; that draft was not a released compatibility baseline. The user expressly authorized version 1.0 and complete contract authoring. No v1.1 evolution or invented legacy interpretation applies.

This document defines producer and conforming-reader requirements. The repository's existing viewer has not implemented all of them. Contract publication does not claim viewer conformance, approve a runtime capacity ceiling, or authorize strategy execution, hosting, authentication or target-product behavior.

## 1. Scope, authority and terminology

The key words MUST, MUST NOT, SHOULD and MAY identify requirements, prohibitions, recommended practices and permitted choices in this specification. MUST rules are conformance requirements. A SHOULD departure requires a stated reason in producer documentation. A producer emits frozen completed-run evidence; a reader inspects it without modifying or calculating replacement strategy evidence.

The canonical normative package uses repository-relative paths: `backtest-data-format.md`, `contracts/editable/run_bundle_contract.json`, `contracts/editable/run_bundle_physical_schemas.json`, `contracts/editable/run_bundle_visual_payload.schema.json` and `contracts/editable/run_bundle_index.schema.json`. The authoring package at `maintenance-cases/MC-2026-10-10-RUN-BUNDLE-CONTRACT-RECOVERY/contract-v1.0.0/` retains identical schemas under the shorter names `manifest.schema.json`, `physical-schemas.json`, `visual-payload.schema.json` and `index.schema.json` used below. Prose owns semantics; the schemas own declared structure/types. A disagreement is a specification defect that blocks a conformance claim; an implementation MUST NOT silently choose one interpretation. Reference tooling and examples are executable evidence, not an authority to amend the contract. JSON Schema structural validation is necessary but does not establish physical, relationship, lifecycle, index or publication conformance.

Definitions:

- **Bundle:** one directory containing one completed run, its manifest, and the indexed immutable evidence reachable from that manifest.
- **Fact:** an immutable producer assertion with stable identity, exact knowledge time and sequence. Knowledge time is simulated historical runner knowledge, not the later wall-clock file-writing time.
- **Occurrence/sample/coordinate time:** when a fill/event occurred or where a point/geometry lies. It is distinct from knowledge time.
- **Reveal minute:** the containing UTC M1 minute of knowledge time. Replay here is minute-granular: all facts within the selected minute are eligible, subject to sequence and lifecycle rules.
- **Logical identity:** an object that can have several historical facts, such as a position, visual or session. It is distinct from a fact/fill ID.
- **Conformant bundle:** all required and declared optional evidence satisfies this package. **Partially inspectable bundle:** a reader can independently establish some evidence despite other unavailable/unsupported evidence; this is not a full-conformance claim.
- **Unavailable:** a declared or required item cannot be read/interpreted. **Empty:** a valid declared section has zero rows. **Absent:** an optional section was not declared. **Insufficient:** required qualified predecessor/state cannot be established within the permitted read. **Refused:** the requested work exceeds the reader's declared budget.

Producer-owned calculations, strategy validity, financial result accuracy and connectedness of strategies are not independently verified by the format reader. Structural references, domains and history coherence MUST be checked. Strings and metadata are inert evidence, never file-access, network-access, HTML or execution instructions.

## 2. Directory topology, discovery and publication

The only manifest name is `manifest.json`. `run.json`, arbitrary JSON discovery, `sections` aliases from the preceding draft, and timestamp-only completion are not canonical alternatives. Selecting a bundle directory opens its manifest; selecting a run root discovers only its immediate non-hidden child directories with a regular `manifest.json`. Descriptors MUST use explicit manifest identity and completion, never folder-name/default identity. Discovery is a candidate listing, not a claim that the bundle is valid. Sort candidates by relative directory name, using UTF-8 byte order. Incomplete/malformed candidates MAY be listed with their explicit status but MUST NOT be described as completed eligible runs.

References are lower-case ASCII relative paths, maximum 240 characters, with components matching `[a-z0-9][a-z0-9._-]*`; separators are `/`. Empty, `.`, `..`, hidden components, absolute paths, backslashes, URI schemes and symlinks are forbidden. Every component and referenced regular file MUST remain inside the selected bundle directory and selected root. Resolve/access checks MUST cover actual consumed manifest, index and shard opens, not just the submitted bundle path. Readers MUST reject escapes before accessing their targets and protect against component replacement races. A selected-root symlink MAY be resolved once as an explicit user selection; references below that resolved root remain symlink-free.

Each shard belongs to exactly one section and is referenced exactly once by that section's time tree. Entity/state trees can reference those same shards; sections MUST NOT share shards or index-node files. There are no default filenames or implicit file probes. Multiple shards are explicitly supported through indexes. Unreferenced files are outside bundle evidence; readers MUST NOT open/hash them merely because they exist. A second `run.json` is inert, not a second manifest.

Publication:

1. Create a new staging directory whose name begins with `.` beneath the intended run root. A producer MUST NOT overwrite or edit an already published bundle.
2. Finish every declared shard and index, close handles, compute references from their final bytes, and validate their consistency. Write `manifest.json` last, initially through a temporary filename, with `completed` exactly boolean `true` and explicit completion wall-clock time.
3. Flush userspace buffers and fsync every evidence file and the staging directory. Atomically rename the entire staging directory to a previously unused non-hidden final directory on the same filesystem; fsync the parent directory. This protocol establishes reader-visible atomic publication and requests crash durability from the local filesystem; it cannot guarantee durability against storage hardware that does not honor syncing.
4. Treat every published file as immutable. A changed run is a new `run_id` and new directory. A byte-identical copy retains run_id; two different manifest contents claiming the same run_id are an identity conflict, not a newer revision.

`completed_at_utc` is wall-clock publication preparation time. It is not used for simulated replay and need not be later than simulated `end_time_utc` if the simulated period is in the wall-clock future. Completion never proves referenced files readable or coherent.

Manifest identity uses SHA-256 of exact manifest bytes. Byte-identical validated copies with the same run_id are interchangeable observations, with independently confined locations; readers may list both locations but MUST NOT merge or double-count their facts. Different manifest digests claiming one run_id are IDENTITY_CONFLICT: withhold those conflicting run candidates until the user selects an explicitly isolated namespace/root or the producer republishes distinct correct identities. Do not choose the newest directory or completion time.

## 3. Common representations and limits

JSON is UTF-8 without BOM, with an object at each manifest/index/payload root. Duplicate keys, NaN/Infinity tokens, nonfinite decoded numbers, invalid Unicode/surrogate code points and nesting beyond 16 containers are invalid. Manifest bytes MUST be ≤1,048,576; each index node ≤65,536; each JSON cell ≤16,384 UTF-8 bytes. Counts, sequences and ordinals MUST be integers, not booleans or numeric strings, in `0..9007199254740991` unless a smaller domain is specified. Other JSON integer tokens have the signed domain `-9007199254740991..9007199254740991`; fractional numbers must decode to finite binary64. No silent coercion or defaulting of evidence is permitted.

IDs match `[A-Za-z0-9][A-Za-z0-9_.:-]{0,127}`. They are case-sensitive, immutable, nonempty, untrimmed tokens. `run_id` is producer-global within its documented namespace; fact IDs are section-scoped within a run; logical object IDs are scoped by object kind within a run. Equal labels or geometry do not establish identity. A producer SHOULD document its run-ID namespace and SHOULD use collision-resistant IDs. References to IDs are explicit; directory names are not identities.

Every instant is an exact UTF-8 string `YYYY-MM-DDTHH:MM:SS.nnnnnnnnnZ`, with nine fractional digits, Gregorian calendar year 1970..9999, valid date/time, seconds 00..59 and explicit Z. A timestamp needing the next minute or nanosecond for an index bound MUST permit that operation within this range; overflow is invalid rather than wrapping or becoming unbounded. Leap seconds, missing/full-offset timezone alternatives, time-only values, logical Parquet timestamps and fractions beyond nine digits are invalid in this version. Producers format their emitted facts to this precision before publication; readers preserve those strings. The fixed representation compares chronologically using byte order; readers MUST validate calendar values before comparison. No local-time conversion, rounding or truncation of an accepted fact is permitted.

Reveal labels are derived, never producer columns: `YYYY-MM-DDTHH:MMZ`. A cursor is a valid reveal label. A fact is revealable if its derived label is ≤cursor. Ordering is by `(reveal_label, sequence_num)`. Sequence MUST be a nonnegative INT64 within the JSON-safe range and unique among distinct facts in the same section and reveal minute, across all objects in that section. Gaps and reuse in later minutes are permitted. Within a minute, a producer MUST assign sequence in nondecreasing exact knowledge-time order; ties use its explicit sequence. There is no cross-section total order and no row-position fallback.

Monetary/prices/quantities/ratios use finite IEEE binary64 values: Parquet DOUBLE and round-tripping JSON numbers. JSON encodings MUST decode to the producer's intended binary64 value. This contract does not promise decimal-arithmetic exactness. Producer rounding is authoritative; readers MUST NOT round stored evidence or recompute authoritative results. Display-only rounding uses manifest decimals or report presentation authority. Negative zero compares equal to zero for duplicate equality. Prices/equity/balance may be zero or negative; quantities are positive per fill and nonnegative where explicitly cumulative/open. Commissions/costs are account-currency debits when positive, credits/rebates when negative; null means unknown, zero means explicitly no charge. Account currency and instrument quote currency are independent fields.

Physical schemas are the exact ordered Arrow/Parquet fields in `physical-schemas.json`. All columns, including nullable columns whose values are entirely null, MUST exist with their declared types and repetition/nullability. Extra/missing/duplicate columns, INT32 substitutes, FLOAT32/decimal substitutes, inferred NULL types and logical timestamp substitutes are invalid. Custom row information goes in JSON cells, not new columns. Parquet dictionary/plain/RLE encodings are allowed; encryption and external column chunks are not. Compression is UNCOMPRESSED or ZSTD. A shard has one row group, at most 4,096 rows, ≤8,388,608 stored bytes and ≤16,777,216 uncompressed row-group bytes. Zero-row shards preserve the complete schema. Parquet metadata MUST contain `bv.contract=run-bundle/1.0.0` and `bv.section=<section name>`.

These fixed limits are storage/interchange constraints, not a benchmarked viewer range ceiling. Readers declare separate finite operation budgets (§11). The physical mappings follow [Apache Parquet logical types](https://parquet.apache.org/docs/file-format/types/logicaltypes/) and its [file layout](https://parquet.apache.org/docs/file-format/); no particular producer library is required.

The file metadata format version is 2.6. Data-page version may be 1 or 2; dictionary/plain/RLE includes the standard PLAIN, PLAIN_DICTIONARY, RLE, RLE_DICTIONARY and BIT_PACKED encoding identifiers. Other encodings are unsupported in this base profile. Arrow schema metadata such as ARROW:schema may be present but MUST NOT contradict the actual physical fields; readers check physical columns as well as reconstructed Arrow types.

`manifest.schema.json` specifies every required key and structural restriction. All listed root keys are required; nullable fields are explicitly present as null when no value is supplied. Unknown root fields are invalid; optional additions use `extensions`.

| `asset_name` | Instrument selection token. It is not a filename or path. |
| `instrument` | `price_unit`, `quantity_unit`, `quote_currency`, `account_currency`; decimals 0..15; `price_basis` BID/ASK/MID/LAST/PRODUCER_DEFINED; optional identity represented by nullable `market_dataset_id`. No implicit dollar/lot/pip assumptions. |

| `start_time_utc`, `end_time_utc` | Simulation interval `[start,end)`, with end strictly later. Final EXIT/CLOSE/session END, events, indicator samples and report samples may occur exactly at end; ENTRY/scaling occurrence must precede end. Knowledge facts, including final full states, must lie in `[start,end]`; geometry can extend beyond it when already known. |

| `primary_strategy_id`, `strategies` | Primary reference and 1..256 distinct catalogue entries (§5). |

| `extensions` | Optional information keyed by producer namespace, e.g. `acme.notes`; unknown values remain inert and MAY be ignored. |

Each section descriptor gives `schema_id`, `optional`, physical-row `row_count` as defined in §6, fixed `time_field`/`entity_field`, `time_index`, `entity_index` and nullable `state_index`. Known values match the physical registry. A file reference is `{path, sha256, bytes}`; sha256 is lowercase hexadecimal SHA-256 of the exact raw file bytes, bytes its positive stored length. Referenced bytes and digests MUST match. JSON key order/whitespace are not canonicalized for file hashing.

Core/optional matrix:

|---|---|---|---|---|

| `strategy_events` | Optional | known_at_utc | event_id | null |

Every declared section, including an empty one, has both time/entity roots; state roots where specified also exist when empty. Empty trees are leaves with entries `[]`. Empty sections have zero physical rows and no shard; a typed zero-row shard MAY instead be indexed with zero row_count and null first/last times. Both representations mean valid empty.

Unknown sections MUST have a namespaced key, namespaced schema_id, `optional:true`, valid generic descriptors/references and the index envelope. They are opaque optional extensions: a base reader withholds them as UNSUPPORTED_SECTION without opening payload shards. No known-core section can be renamed into an extension to evade its requirements. Named unknown `required_features` govern explicit required semantics; unrecognized section/geometry data alone does not change the bundle version.

Market matching is a separate claim. A reader MAY offer a name-based candidate but MUST NOT label source equivalence verified from equal names or “contains a Parquet.” Verified correspondence requires equality of explicit producer dataset identity and qualified local dataset identity, plus matching instrument/unit/side/time coverage under local market authority. With absent/unverifiable identity, the run remains inspectable in run-only mode or with an explicitly unverified candidate. No source_data_location is followed automatically.

## 5. Strategy, session and setup identity

Each strategy catalogue row gives `strategy_id`, `name`, opaque nonempty `version`, `parent_strategy_id`, `known_at_utc` and metadata. The primary has null parent; every other entry references an earlier catalogue entry, ultimately reaching the primary. IDs are unique and cycles are invalid. This is an emitted relationship claim, not proof that strategies are substantively connected. A producer MUST NOT place independent strategies in one run; the reader checks reference structure but does not judge connectedness. Catalogue labels/metadata are withheld before their knowledge minute. An attributed fact cannot precede the referenced strategy's knowledge instant.

Strategy attribution is nullable on executions/position history. Null is explicitly unassigned: it remains visible with no strategy filter and does not match any chosen strategy. All facts for one position use the same attribution/setup token/session association. Selecting a strategy filters trades/positions only. Visual/indicator/session evidence remains run-level under its normal time, geometry and availability rules. No non-trade strategy attribution is required or inferred. Overlapping sessions may produce overlapping run-level evidence; selection does not authorize suppression.

`setup_id` is an optional opaque grouping token scoped to a run. There is no setup catalogue or setup lifecycle in v1.0.0. Repeated tokens claim grouping only; events may explain progression. A missing token does not authorize reconstruction of a setup.

Session rows are independent START/END facts, not inferred from trades or a trading calendar. Each session has exactly one START followed by exactly one END, same ID and label, boundary start < boundary end, boundaries in the simulation interval including final end, known_at ≥boundary. START and END are each valid and independently navigable when revealed. Their labels/metadata carry only knowledge at that boundary fact. Sessions may overlap/nest/abut, contain no trades and start before any trade. Sort navigation by `(start reveal minute, START sequence, session_id)`; strategy selection never removes an established session start. END boundaries/details remain withheld before END knowledge even though the completed-file indexes can contain them.

Non-null session references MUST resolve to a session whose START is known by the referencing fact. Session association is producer attribution, not a claim that every geometry coordinate/fill lies within session boundaries, and not visual strategy relevance. Missing/unreadable session evidence affects navigation/reference confirmation, not independently established trade or visual values.

## 6. Fact identity, duplicates and executions

Every physical row has non-null `fact_id`, `known_at_utc`, `sequence_num` and `metadata_json`. Metadata is a strict bounded JSON object; it must contain only information already known at the row's knowledge time. Fact IDs identify immutable facts, not revisions. A row correction is not written under an old ID.

Identical repeats of the same fact_id are allowed and collapse to one semantic fact. Equality covers every defined field, including all decoded JSON data and optional metadata; object key order/JSON whitespace are irrelevant, array order remains significant, JSON numbers compare numerically (1 equals 1.0), boolean values never equal numbers, Parquet scalars retain their declared types, and canonical timestamps compare exactly. Conflicting repeats invalidate that fact and its dependent history; no “first row wins.” Sequence uniqueness applies to distinct deduplicated facts. `row_count` counts physical rows, including identical repeats; index time/entity coverage covers all physical rows, while effective-state resolution deduplicates. Reader evidence/counts MUST NOT double-count repeats.

Trade rows represent individual executed fills, not orders or closed-trade pairs. `execution_id=fact_id`; `position_id` is required. Occurrence `timestamp_utc` ≤knowledge and within simulation bounds, with final EXIT at end permitted. `quantity` is positive per-fill size; `price` is finite instrument-price value. Side is BUY/SELL; action is ENTRY/SCALE_IN/SCALE_OUT/EXIT. A position begins with exactly one ENTRY and ends with at most one EXIT; scaling requires an entered, not yet exited position. ENTRY/SCALE_IN sides equal the opening direction; SCALE_OUT/EXIT sides are opposite. Partial fills are separate executions, not guessed from cumulative quantity. A reversal closes the old position and starts a new ID; hedged opposite positions have different IDs. Open positions at completed-run end are legal.

`realized_gross_pnl` is the producer's incremental realized account-currency amount attributed to this fill, before commission/other costs. It may be null when not supplied; it is never a final position outcome emitted early. `commission`/`other_costs` are incremental known charges/credits, nullable when unknown. Reader MUST NOT sum them into an authoritative report or infer absent amounts as zero. Optional strategy/setup/session associations follow §5. Execution metadata and timestamps contain no later closing/outcome facts.

`position_history` contains authoritative producer full-state snapshots. OPEN must be first, UPDATE requires a still-open predecessor, CLOSE is terminal and requires a previously opened position and zero open_quantity. OPEN's last_execution_id equals entry_execution_id; subsequent references identify known executions of this same position. The immutable direction, entry ID/time/price/initial quantity and associations do not change. LONG means opening BUY, SHORT opening SELL. Entry time/price/quantity must match the referenced ENTRY fact; last_execution must be known by the snapshot. Totals/open quantity are current producer-emitted values, not future maxima. Quantities are nonnegative; initial_quantity and total_entry_quantity are positive. A CLOSE has non-null net_pnl, exit_time and nonnegative duration, references the position's EXIT, and exit_time equals that occurrence; non-CLOSE rows require those three fields null. Current realized_net_pnl can be unknown/null and is distinct from final outcome. The viewer displays these emitted values, not first/last/max heuristics or recomputed PnL. Final snapshots may persist for historical inspection.

## 7. Events

Event IDs equal fact_id and name unique immutable event facts. `event_type` is a nonempty inert producer classification of ≤128 characters; unknown types are displayed as labelled events without executing their meaning. `timestamp_utc` is occurrence ≤knowledge. Message is nullable inert text ≤4,096 characters. Nullable position/execution/strategy/setup/session links have the meanings above; execution references must be known and belong to any supplied position. Dangling references are structural defects in the affected event, not a license to infer them. Event replay is governed by knowledge time, including retrospectively discovered occurrences. Events are independent optional evidence; they do not supply hidden defaults for other sections.

## 8. Visual geometry and history

Visual IDs name logical objects; lifecycle fact IDs name changes. CREATE is first, UPDATE requires an effective predecessor, REMOVE requires an effective predecessor and is terminal. A later new level has a new visual_id. All changes retain the same nullable session association. UPDATE is a complete replacement of payload/geometry/metadata, never a patch; a missing field is invalid or explicitly null, not inherited. A producer may change geometry kind when it still claims the same logical object; a reader unable to interpret the new kind withholds that form rather than keeping a stale old form. Historical changes remain individually inspectable even when several share a minute.

CREATE/UPDATE require `geometry_type` and `payload_json`, null removal_reason. REMOVE requires null geometry_type/payload_json and optional ≤1,024-character removal_reason. No “action BUY” geometry inference or flattened price aliases are legal. Payload exactly matches `visual-payload.schema.json`: geometry, nullable label/method, style object and extensions object. geometry_type equals geometry.kind. Method has inert name/parameters/metadata; EMA/Fibonacci/percentage/support/resistance provenance never authorizes a calculation or chooses geometry. Display styles have no strategy relevance.

| Geometry kind | Complete geometry fields and meaning |
|---|---|
| `HORIZONTAL_LEVEL` | `kind`, finite `price`; temporal extent starts at its creation knowledge minute and remains until explicit update/removal. No implicit expiry. |
| `PRICE_ZONE` | `kind`, finite `price_low`, `price_high`, low ≤high; same lifecycle persistence as a horizontal level. A zero-height zone is legal. |
| `TREND_LINE` | `kind`, exact start/end times with start <end, finite price_start/price_end. Straight finite segment, no extrapolation; endpoint is included. All geometry was known at the emitting fact. |
| `BOX` | `kind`, exact start/end with start <end, price_low ≤price_high. Closed price bounds, horizontal `[start,end)` extent. ORB is provenance, not a separate calculated primitive. |
| `MARKER` / `ARROW` | `kind`, exact time_utc, placement PRICE/ABOVE_BAR/BELOW_BAR, nullable price, direction. PRICE requires finite price; bar placements require null. Arrow direction UP/DOWN; marker permits NEUTRAL. No side/name inference. |
| Namespaced unknown kind | Opaque bounded geometry object whose kind matches the namespace grammar. Valid optional extension envelope, unsupported geometry for a base reader. No visual approximation. |

Known geometry can have a future coordinate/endpoint; its entire payload must have been known at the emission instant. Knowledge is asserted by the producer's row; readers do not verify the strategy calculation or treat endpoint time as knowledge. Geometry cannot be revised retroactively without a later UPDATE fact and distinct fact_id. Native v1.0 kinds and namespaced optional kinds can coexist under one envelope; there is no “legacy v1.0 versus v1.1” discriminator.

Style properties are optional: absent color defaults to neutral `#64748B`, line_width to 1, line_style SOLID and opacity 1. These are presentation defaults, not evidence values. Styles cannot override geometry, time, quantity, identity or knowledge. Label null displays the stable ID; labels never determine support/resistance role or geometry.

At each reveal minute, all changes are ordered and retained; the last sequence for one visual is its effective form. An effective form lasts on `[its reveal minute,next effective change's reveal minute)`; REMOVE has no drawable form. If CREATE then REMOVE occur in the same minute, replay at that minute draws neither, while both historical changes remain inspectable. A missing/conflicting/invalid predecessor makes the affected history insufficient from that point; never manufacture a valid earlier/current form across uncertainty.

In FULL_HISTORY, draw historical effective forms clipped to their effective periods, requested viewport and geometric extent. In REPLAY, choose the last qualified form by cursor, then clip its declared geometry to the viewport; a known future endpoint may remain visible even beyond the market replay cursor. Market candles/future-discovered facts remain subject to their own no-lookahead policy. Price-bound geometry uses the manifest instrument-price axis; above/below-bar markers require a qualified containing bar or remain unavailable, never fabricated. At higher display timeframes, align marker placement to the containing candle while preserving exact source coordinates/detail.

## 9. Indicator series and points

Series rows are immutable catalogues; fact_id=series_id, one semantic row per ID. Names, component, unit, axis, method/style/metadata and nullable session association are emitted at catalogue knowledge. Each component of a multi-value indicator has its own series_id; related names do not merge identities. PRICE axis requires unit exactly equal to instrument.price_unit; SEPARATE means a labelled separate scale in that declared unit. Methods and parameters are explanation only.

Points reference a catalogue already known by their knowledge instant. sample_time ≤known_at. One semantic point per `(series_id,sample_time)` is permitted; identical fact repeats collapse, conflicting samples invalidate those points. Corrections, deletion and revising an earlier sample under a new ID are explicitly excluded in v1.0.0; use a distinct series ID for a revised series. `status=VALUE` requires a finite value; WARMUP/GAP require null. Zero is a valid VALUE. No array-valued cells or viewer-computed EMA/levels exist.

Display only qualifying emitted samples. Adjacent VALUE points may be connected by a straight cosmetic line; GAP/WARMUP breaks the line. No extrapolation, new sample synthesis, smoothing, resampling or hidden thinning is allowed. A predecessor point needed to establish continuity is fetched through the entity index and must also satisfy knowledge gating. If the nearest earlier sample is unrevealable, continue only within the declared budget; exhaustion is insufficient, not proof of absence. The series/sample indexes supply points in coordinate order while retaining distinct knowledge time. All indicator evidence remains run-level under strategy filtering.

## 10. Authoritative reports

Report is required. Each of summary/trade_stats/drawdown is either its complete schema object or null. `unavailable_reasons` contains exactly the null category keys with inert nonempty reasons; non-null categories have no unavailable reason. Missing keys, present empty objects or mistyped metrics are invalid, never zero-filled. All optional/undefined scalar metrics are explicitly nullable fields in an available category. Null means not supplied or mathematically undefined; readers show unavailable, never invent Infinity or zero. Zero-trade and entirely unavailable-category runs are legal with explicit states.

All report amounts are account currency. Report calculations are producer assertions; the reader validates domains and stated counts, not strategy-result correctness. Counts are completed positions, not fills; open positions at end are excluded. Break-even net outcomes count in total_trades but neither winning nor losing. winning+losing must not exceed total. Missing optional sections do not justify changing the producer report.

| Metric | Required meaning |
|---|---|
| `total_net_profit` | Sum of final net outcomes of completed positions, including trading costs/credits. |
| `gross_profit`, `gross_loss` | Sum of positive gross realized completed-position outcomes and absolute sum of negative gross outcomes respectively, before costs; both nonnegative. |
| `total_trades` | Completed-position count. |
| `profit_factor` | gross_profit/gross_loss; null if gross_loss=0. |
| `expected_payoff` | total_net_profit/total_trades; null for zero trades. |
| `return_on_max_drawdown` | total_net_profit/max_drawdown; null for zero/unavailable drawdown. |
| `winning_trades`, `losing_trades`, `win_rate` | Positive/negative final net position outcomes; win_rate=winning/total, a fraction 0..1, null for zero total. |
| `average_win`, `average_loss`, `win_loss_ratio` | Average positive net outcome and average loss magnitude; null if relevant class empty; ratio average_win/average_loss, null when undefined. |
| `max_consecutive_wins`, `max_consecutive_losses` | Longest runs of positive/negative net outcomes in closing `(reveal minute, EXIT sequence, position_id)` order. Break-even breaks both streaks. Null if not supplied; zero is valid. |
| `largest_winning_trade`, `largest_losing_trade` | Maximum positive net amount / maximum net loss magnitude; null if relevant class empty. |
| `average_trade_duration_seconds` | Arithmetic mean of producer holding durations of completed positions; null for zero/not supplied. |
| `max_drawdown` | Largest peak-to-subsequent-trough absolute equity decrease over producer equity observations, nonnegative; zero when no decrease. |
| `max_drawdown_pct` | Fraction decrease/preceding equity peak for the interval achieving max_drawdown; null if peak≤0 or unavailable. This is a fraction, not percent points. |
| `relative_drawdown_pct`, `relative_drawdown` | Greatest valid equity drawdown fraction using positive preceding peak, and absolute decrease for that same interval; null together when undefined/not supplied. |

The equity_curve section carries exact timestamped producer mark-to-market equity and realized balance, including known costs, in account currency. Coordinates are unique, increasing across semantic points and within `[start,end]`; gaps/sparse points are allowed. Sparse observations do not claim continuous verification. Display positions use elapsed timestamp, not row index; equity may connect adjacent observations and balance may step between them as cosmetic drawing, with no invented values treated as evidence. A reader MUST NOT claim calculated peak/trough/drawdown/YTD as authoritative producer metrics; such derived analytics are excluded from this read-only evidence contract.

monthly_returns has unique year/month rows within the run's UTC month span. Sparse absent months are unavailable, not zero. profit is final net position outcomes whose final exit occurrence lies in that month. trades_count uses that same population. return_pct is **percent points**, `100 * profit / opening equity for that month`; null if opening equity is zero/not supplied. A partial first/last month uses the run boundary as its opening/closing extent. Negative opening equity is legal and the producer's signed percentage is retained. No YTD metric is supplied in v1.0; reader MUST NOT label the sum of monthly percentages as emitted YTD. Monthly facts are known_at=end_time_utc. No inline equity/monthly arrays are valid manifest fields.

All report categories and both report sections are disclosed only in FULL_HISTORY or when replay cursor reaches the containing minute of end_time_utc. Opening a bundle while replay is earlier MUST NOT expose full report values through its API, diagnostics or nested metadata. This requirement is a reader obligation; the on-disk completed bundle is not confidential against its local owner.

## 11. Indexed access and bounded outcomes

Every section has time and entity trees; stateful sections also have a state tree. `index.schema.json` defines exact JSON envelopes. Nodes declare index_kind, level, summary and entries; leaves have level=0. Branch entries reference child bytes and copy their exact summaries. A branch has 1..64 children; a leaf has 0..64 entries. Depth is ≤32, all leaves of one tree have the same level distance, node files are unique to one tree, and cycles/sharing between branches are invalid. Digests bind every consumed node/shard to the manifest root. Entry order is ascending by the key definitions below. Exact summary values and full coverage are producer requirements verified by the full reference validator.

Time-leaf entries reference shard bytes plus physical row_count and first_time/last_time from the section's time_field. Shards are physically sorted by `(time_field, known_at_utc, sequence_num, fact_id)`. Global shard ranges are ordered and may share a boundary value. Nonempty shards have exact min/max times; zero-row shards have both null. Time summary min_key/max_key are earliest/latest indexed coordinate; count is physical rows. For a viewport `[a,b)`, select entries with last_time≥a and first_time<b, then filter rows exactly. Equity final sample at end can be queried through an explicit closed-end request; ordinary viewport remains half-open.

Entity leaves have one reference per physical row: entity_id, time_utc (the section time_field), known_at_utc, sequence_num, fact_id, file and zero-based row. Their key is `entity_id + '|' + time_utc + '|' + sequence_num padded to 16 decimal digits + '|' + fact_id`. IDs cannot contain `|`. Summary min_key/max_key are those exact key extrema; count is physical row references. Entity/time coverage must reference exactly the same rows, including identical repeats. An entity seek/range/predecessor uses key bounds and visits only relevant branches; it does not scan the entire entity catalogue to find a known ID.

State leaves reference each effective deduplicated full-state fact, with entity_id/fact_id/file/row, `known_from_utc`, nullable `known_to_utc`, `coordinate_start_utc` and nullable `coordinate_end_utc`. Known bounds are canonical instants at reveal-minute starts; end is the next effective change minute, null unbounded. REMOVE yields no state entry; session END yields a preserved ended-session form; position CLOSE yields a preserved closed-position form. Superseded same-minute facts remain in time/entity indexes but not state entries. State key is `coordinate_start_utc + '|' + known_from_utc + '|' + fact_id`; ordering uses that key. All three index kinds use summary fields min_key/max_key/count/min_start/max_end/min_known/max_known_end; the last four are null for time/entity trees. In a nonempty state summary min_start/min_known are minima; max_end/max_known_end are maxima, with null meaning unbounded if any corresponding entry is unbounded. In an empty summary all extrema are null and count=0.

Coordinate bounds conservatively cover geometry: persistent levels/zones begin at first CREATE reveal minute and end unbounded; segments/boxes use geometric start/end, markers use the containing coordinate minute `[minute,minute+1min)`; opaque geometry spans the entire run. Position states use entry occurrence through final exit's containing minute plus one minute for CLOSE, otherwise unbounded. Session states use START boundary through END's containing minute plus one minute for END, otherwise unbounded. These indexed bounds are selection hints, never early-disclosed future facts. A TREND_LINE's included endpoint requires its index end one nanosecond beyond the endpoint; BOX end is already exclusive. Branch summaries may overselect because they combine independent dimensions; they MUST NOT exclude any qualifying child.

For REPLAY state selection, prune only when coordinate bounds cannot intersect viewport or known intervals cannot contain the cursor's minute start; then inspect exact state intervals/geometry and resolve references. FULL_HISTORY selection uses both effective-period and geometry intersection with viewport. Needed predecessor/entity/catalogue references consume the same explicit request budget. A missing/broken/unsupported state index or exhausted predecessor search produces scoped INSUFFICIENT_HISTORY; never declare absent or retain a stale form by scanning unindexed history as hidden fallback. Independent sections/objects already established can remain available.

A reader MUST declare finite limits for manifest/index bytes, nodes, shard bytes, rows/points, predecessor steps and elapsed work, with a named supported local configuration. Such a profile is separate from producer file validity. Preflight using counts/byte descriptors when sufficient; refuse an over-limit requested range as REFUSED_OVER_LIMIT before dependent work when it can be determined. If uncertainty/exhaustion is discovered during permitted work, stop and return INSUFFICIENT_HISTORY or REFUSED_OVER_LIMIT as applicable; no partial sample set presented as successful full evidence. An explicitly narrower user request is separate, not hidden recovery. No automatic candle resolution change, aggregation, thinning, resampling, paging through an over-limit request or whole-history fallback is permitted. Explicit bounded detail-history pages are legal separate user requests.

Completeness of producer indexes is an evidence assertion with normative full-coverage rules, not proof of runner correctness. A full conformance audit can verify indexes against every declared physical row. A bounded reader verifies consumed nodes/shards and local bounds/relationships and reports whether it has full-validation evidence for the immutable manifest digest or only scoped validation. It MUST NOT claim independently verified whole-bundle/index completeness from a partial read, nor guess absence when required predecessor proof is unavailable. Conformant producer declared state coverage can support scoped selection; detected inconsistencies invalidate the affected scope. Default UI work never performs a whole-run conformance audit implicitly.

## 12. Integrity, observation and validation

Before parsing any referenced content, read exactly the declared bytes within the file-size/budget limit and verify SHA-256. Parse those same consumed bytes; do not hash one generation and reopen a different generation for rows. Protect actual opens against symlink/path races, retain file/directory identity and check before/after identity/size/mtime/ctime where available. Before publication of a read result, verify consumed source identities still match and re-read/check manifest identity/digest. A detected mutation yields OBSERVATION_CHANGED; discard that candidate result. A SHA-256 content reference is coherence/integrity evidence, not source authentication, a lock, a universal race detector or proof of unchanged unconsumed files.

Validation order: confined strict manifest/version/core feature parse; descriptor/domain checks; referenced-node/shard integrity/physical type checks; row shapes/scalars; semantic duplicate/sequence/reference/lifecycle checks; index coverage/state checks; requested temporal/geometry projection; observation/current-context checks. Whole-conformance tools may traverse all declared data explicitly. Bounded readers may qualify independent evidence incrementally without claiming full validation.

| Condition | Required reader outcome |
|---|---|
| Missing/invalid manifest, no true completion, missing identity/version, unknown required feature | Whole run unavailable/unsupported; no invented core defaults. |
| Missing/corrupt/schema-invalid required trade_facts or required core index | Core run cannot be accepted. A valid zero-row core is eligible. |
| Optional section absent | ABSENT; no warning claiming corruption and no implicit file probe. |
| Declared valid empty section | EMPTY; independently proven zero rows. |
| Optional file/index corruption or type failure | WITHHELD_SECTION with attributable reason; retain independent core/optional evidence. |
| Bad optional row, conflicting ID, bad sequence/reference | WITHHELD_FACT or dependent entity/history; widen only when independence cannot be established. A conversion exception must not escape this fault boundary. |
| Unknown optional geometry/section | UNSUPPORTED_GEOMETRY/UNSUPPORTED_SECTION; preserve supported independent evidence, no approximation. |
| Unestablished predecessor or broken history | INSUFFICIENT_HISTORY; no affected current form and no guessed absence. |
| Over-budget range | REFUSED_OVER_LIMIT, with limits/scope; no substitute representation. |
| Detected source/context change | OBSERVATION_CHANGED / STALE_CONTEXT; no current success from the old candidate. |
| Explicit unavailable report category or unassigned trade attribution | Preserve that exact meaning; do not treat unavailable as zero or unassigned as a matching strategy. |

Diagnostics identify stable reason code, section, optional fact/entity identity and safe bounded explanation. Code names in this table are canonical categories; reader subcodes may be namespaced. Do not expose raw secret-like/future payloads through warnings; metadata is not trusted executable markup. Limit diagnostics with explicit suppressed count. A malformed/unsupported field is never fabricated as a valid fact. Current root/bundle/manifest digest/range/cursor/strategy selection must bind every delivered result and warning; strategy selection affects trades only.

## 13. Versioning, extensions and reader support

`format_version` uses three nonnegative decimal components with no leading zeros except zero itself; prerelease/build labels and missing/malformed versions are unsupported/invalid here. The v1.0 producer emits exactly `1.0.0`. An implementation MUST declare the exact contract versions/profiles it supports; the reference tools support 1.0.0 base plus opaque optional extension envelopes. The present viewer has no demonstrated complete-v1.0 support claim.

Future minor/patch contracts within a major retain earlier required meanings/bytes and add only safely ignorable optional information; a newer reader declaring support for that major must retain published earlier interpretations. An older reader accepts a later compatible revision only if its stable envelope/core feature policy can validate the recorded required meaning; it MUST distinguish unsupported optional data and must not pretend to enforce unknown new semantics. Breaking interpretation/physical requirements need a new major with a separate titled specification and support decision. Previously declared supported released versions remain readable through explicit retained interpretations.

An unknown major is not parsed as v1 just because familiar keys occur. Readers can show bounded inert discovery facts but semantic sections are UNSUPPORTED_VERSION unless a separately specified stable envelope grants independence. No such cross-major semantic envelope is defined in v1.0.0. Unknown required features block whole acceptance; namespaced optional metadata, sections and geometry are ignored/withheld by explicit rules, without changing the recorded version. Known standard fields cannot be shadowed by extensions. Extension content shares ordinary size/knowledge/security limits.

The preceding draft and current empirical reader tolerances have no automatic support profile. Actual retained nonconforming bundles, if later supplied, require an explicitly named and tested empirical adapter; their recorded format strings MUST NOT be rewritten. No draft-era aliases, UPDATE-before-CREATE, missing fields/defaults or flattened geometry become canonical merely because old tests accept them.

## 14. Producer procedure, examples and conformance

An implementation may emit bytes using any compatible libraries. The standalone reference producer constructs explicitly typed tables and indexes from JSON input independently of viewer and validator logic. Its CLI invokes the separate validator on completed staging bytes before publication; its explicit low-level fixture mode can intentionally emit invalid semantic inputs for testing. Run the accompanying producer and full validator to inspect a concrete example containing execution/scaling evidence, EMA points, an ORB box, an emitted Fibonacci-method level, prospective update/removal, independent session starts and authoritative reports. A validator can test structure/content/index coherence but cannot prove historical truth, publication fsync execution or strategy-result correctness from bytes alone; reports explicitly state those limits. A producer's required attestation is its conformance claim and documented publication behavior, not an invented cryptographic certificate.
